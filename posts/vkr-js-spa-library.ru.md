# VKR SPA Library: Framework-Agnostic JavaScript-библиотека

**🏫 Академический проект:** Данная работа выполнена в рамках Выпускной квалификационной работы (ВКР) в Самарском национальном исследовательском университете.

## 📋 Аннотация

В данной выпускной работе представлены проектирование, реализация и оценка **VKR SPA Library** — модульной JavaScript-библиотеки для построения одностраничных приложений (Single-Page Applications, SPA) без зависимостей от популярных фреймворков, таких как React или Angular. Библиотека решает потребность в легковесных, легко интегрируемых решениях, которые снижают порог входа в разработку SPA, предоставляя при этом необходимые современные функции.

Основным вкладом является четырехуровневая архитектура, реализующая клиентскую маршрутизацию, централизованное и персистентное управление состоянием, набор переиспользуемых UI-компонентов и уникальную клиентскую административную панель для управления контентом. Система использует чистый ES6+ JavaScript, проверенные паттерны проектирования и современные Web API. Пользовательский пайплайн сборки на основе Gulp обеспечивает совместимость и оптимизацию. Проект включает полную UML-документацию, тестирование производительности и сравнительный анализ с существующими решениями (React, Vue.js, jQuery UI), подтверждая практическую полезность для прототипирования и веб-проектов среднего масштаба.

**Ключевые слова:** Одностраничное приложение, JavaScript-библиотека, Клиентская архитектура, Управление состоянием, UI-компоненты, Система управления контентом, Модульный дизайн, UML

## 1. Введение и анализ проблемы

Современная веб-разработка требует высокоинтерактивных и отзывчивых пользовательских интерфейсов. В то время как традиционные многостраничные приложения (Multi-Page Applications, MPA) вызывают полную перезагрузку страницы, ухудшая пользовательский опыт, одностраничные приложения (SPA) загружают единственную HTML-страницу и динамически обновляют контент. Популярные фреймворки, такие как React и Vue.js, решают эту задачу, но привносят комплексность: тяжелые конфигурации сборки, глубокие знания экосистемы и большие размеры бандлов.

Данный проект определяет нишу для **легковесной, framework-agnostic библиотеки**, которая:

- Подключается одним тегом `<script>` без этапа сборки.
- Предоставляет основные механизмы SPA (маршрутизацию, управление состоянием).
- Включает готовый набор стилизованных UI-компонентов.
- Интегрирует **клиентскую административную панель** для редактирования контента в реальном времени — функция, отсутствующая в большинстве аналогичных библиотек.

Целью было создание инструмента, упрощающего разработку SPA для образовательных целей, быстрого прототипирования и проектов, где накладные расходы фреймворков нежелательны.

## 2. Анализ предметной области и сравнительное исследование

### 2.1 Основные концепции

Библиотека построена на четко определенных концепциях SPA:

- **Компонент:** Самодостаточный блок пользовательского интерфейса с собственной логикой, шаблоном и стилями (например, карусель, модальное окно).
- **Модуль:** Логически завершенный набор функций (например, Роутер, Хранилище, HTTP-клиент), регистрируемый в центральном ядре.
- **Клиентская маршрутизация:** Механизм, сопоставляющий изменения URL (hash/History API) с конкретными компонентами без перезагрузки страницы.
- **Централизованное состояние (Store):** Глобальный контейнер данных, синхронизируемый между компонентами с использованием паттерна Наблюдатель (Observer).
- **Персистентное хранилище (Storage):** Кэширование данных на стороне клиента с использованием Web Storage API (localStorage).
- **Административная панель:** Интерфейс, встроенный через `<iframe>`, позволяющий выполнять CRUD-операции над контентом страниц, метаданными и резервными копиями без доступа к серверу.

## 3. Проектирование системы и архитектура

### 3.1 Концептуальная модель и слоистая архитектура

Библиотека структурирована в четыре различных логических уровня для обеспечения разделения ответственности, модульности и простоты расширения.

![Концептуальная модель JavaScript-библиотеки для SPA](1.png)
_Рисунок 1: Четырехуровневая концептуальная модель: Ядро, Сервисы, UI-компоненты и Шаблоны/Стили._

- **Уровень Ядра:** Отвечает за инициализацию библиотеки и управление глобальным **Реестром** модулей. Все функциональные модули регистрируются здесь при загрузке.
- **Сервисный уровень:** Содержит основные модули бизнес-логики: **Роутер** для навигации, **Хранилище (Store)** для глобального состояния, **Персистентное хранилище (Storage)**, **HTTP-клиент** для обмена с сервером и модуль **Административной панели**.
- **Уровень UI-компонентов:** Коллекция переиспользуемых, самодостаточных виджетов интерфейса (кнопки, формы, карусели, модальные окна) с унифицированным API жизненного цикла.
- **Уровень Шаблонов и Стилей:** Управляет представлением через SCSS-модули, CSS-переменные для динамической темизации и обрабатывается через PostCSS для оптимизации.

### 3.2 Структурное проектирование

Высокоуровневое взаимодействие между клиентской частью библиотеки и серверным бэкендом для админ-панели определено в структурной схеме.

![Структурная схема библиотеки](2.png)
_Рисунок 2: Структурная диаграмма, иллюстрирующая взаимодействие модулей и клиент-серверную коммуникацию для функциональности администратора._

### 3.3 Динамическое поведение: активность загрузки страницы

Последовательность операций во время навигации пользователя критически важна для отзывчивости SPA.

![Диаграмма деятельности библиотеки при загрузке страницы](3.png)
_Рисунок 3: UML Диаграмма деятельности, детализирующая пошаговый процесс от инициализации библиотеки до рендеринга страницы и сохранения состояния._

Последовательность выглядит следующим образом:

1.  **Инициализация:** Загружается основной скрипт библиотеки, регистрируются модули и запускается роутер.
2.  **Навигация:** Действие пользователя инициирует изменение маршрута.
3.  **Разрешение и загрузка модуля:** Роутер проверяет, загружен ли целевой модуль, и при необходимости загружает его динамически (`import()`).
4.  **Получение данных и обновление состояния:** Компонент инициализируется, отображается индикатор загрузки, данные получаются через HTTP-клиент и обновляется центральное хранилище.
5.  **Рендеринг и завершение:** Компонент рендерится с новыми данными, индикатор скрывается, и текущий маршрут сохраняется в `localStorage`.

## 4. Детали реализации

### 4.1 Обоснование технологического стека

- **Язык:** **Vanilla JavaScript (ES6+)** для современного синтаксиса (модули, классы, промисы) без зависимости от транспиляции для разработки.
- **Стилизация:** **SCSS** для модульных, темизируемых стилей и **PostCSS** для авто-префиксов и минификации.
- **Автоматизация сборки:** **Node.js** и **Gulp** создают пайплайн для транспиляции (Babel), компиляции SCSS, объединения и минификации файлов для продакшена (`lib.js`, `styles.css`).
- **Бэкенд (Админ-панель):** **PHP** с REST API (`checkAuth.php`, `savePage.php`) предоставляет простые CRUD-эндпоинты, тестируемые с **MAMP**.
- **Инструментарий:** **VS Code** для разработки, **Chrome DevTools** для отладки и профилирования производительности.

### 4.2 Архитектура компонентов

Библиотека реализована как набор связных, слабосвязанных модулей.

![Диаграмма компонентов библиотеки](4.png)
_Рисунок 4: UML Диаграмма компонентов, показывающая зависимости между основными модулями библиотеки и внешним Admin API._

Ключевые реализованные модули включают:

- **`Ядро` & `Реестр`:** Загрузчик и менеджер зависимостей модулей.
- **`Роутер`:** Обрабатывает навигацию на основе hash, сопоставление маршрутов и ленивую загрузку.
- **`Хранилище (Store)`:** Простая реализация Observable для глобального состояния.
- **`Персистентное хранилище (Storage):** Обертка вокруг `localStorage` с сериализацией и управлением временем жизни (TTL).
- **`HTTP-клиент`:** Обертка над Fetch API с централизованной обработкой ошибок и управлением токенами авторизации.
- **`Админ-панель`:** Самостоятельное SPA, загружаемое в iframe и взаимодействующее с PHP API.
- **`UI-компоненты`:** Реализованные виджеты, следующие единому жизненному циклу (`init()`, `render()`, `destroy()`).

### 4.3 Архитектура развертывания

Библиотека функционирует в определенной среде развертывания, от разработки до поставки в продакшен.

![Диаграмма развертывания библиотеки](5.png)
_Рисунок 5: UML Диаграмма развертывания, иллюстрирующая пайплайн сборки и среду выполнения._

1.  **CI/CD Сервер (Gulp):** Центр разработки. Транспилирует ES6+ в ES5, компилирует SCSS, объединяет и минифицирует ассеты.
2.  **Статический сервер (CDN):** Хостит финальные бандлы библиотеки (`lib.js`, `styles.css`) для высокодоступной доставки.
3.  **Браузер:** Основная среда выполнения. Загружает ядро библиотеки, динамически импортирует модули и размещает админ-панель внутри iframe.
4.  **Веб-сервер:** Обслуживает основной `index.html` и хостит контент iframe админ-панели.
5.  **API Сервер (PHP):** Предоставляет RESTful бэкенд для всех операций админ-панели (аутентификация, CRUD-операции со страницами, управление резервными копиями).

### 4.4 Ключевые технические реализации

- **Паттерн Реестр:** Все модули саморегистрируются в ядре, обеспечивая слабую связанность и динамическое обнаружение.
- **Паттерн Наблюдатель для состояния:** `Хранилище (Store)` уведомляет все подписанные компоненты об изменениях состояния, обеспечивая согласованность UI.
- **Ленивая загрузка:** Компоненты маршрутов загружаются по требованию с использованием динамического `import()`, оптимизируя время начальной загрузки страницы.
- **Безопасность админ-панели:** Панель работает в изолированном `<iframe>`, отделяя её от основного DOM приложения для безопасности и стабильности.

## 5. Тестирование и оценка производительности

Для проверки функциональности и эффективности использовалась строгая стратегия тестирования:

1.  **Модульное тестирование (Jest):** Основные модули (Роутер, Хранилище, HTTP-клиент) были протестированы с >20 тестами каждый, с фокусом на инициализацию, сериализацию и обработку ошибок. Время выполнения: ~120 мс.
2.  **Интеграционное тестирование (Puppeteer):** Имитировались реальные пользовательские сценарии: навигация, отправка форм, CRUD-операции в админ-панели. Фиксировались метрики, такие как Time to Interactive (TTI) (например, загрузка страницы каталога: ~480 мс).
3.  **Анализ производительности (Lighthouse):** Проведено бенчмаркирование демо-приложения:
    - **First Contentful Paint (FCP):** `620 ± 30 мс`
    - **Time to Interactive (TTI):** `1200 ± 80 мс`
    - **Общее время выполнения JS:** `50 ± 5 мс`
4.  **Профилирование памяти (DevTools):** Рост потребления памяти был ограничен <15 МБ при интенсивной навигации с правильной очисткой после уничтожения компонентов.
5.  **Нагрузочное тестирование (Apache Bench):** Admin API обрабатывал ~200 запросов в секунду со средним временем ответа `80-120 мс`.

**Результаты:** Библиотека продемонстрировала функциональную полноту, эффективное потребление ресурсов и стабильную производительность под нагрузкой, подтвердив готовность к практическому использованию.

## 6. Заключение

Проект VKR SPA Library успешно достиг своей цели: спроектировать и реализовать функциональную, самостоятельную JavaScript-библиотеку для построения одностраничных приложений. Работа вносит несколько конкретных вкладов:

1.  **Архитектурное проектирование:** Четко определенная, четырехуровневая модульная архитектура, которая чисто разделяет ответственность и облегчает расширение.
2.  **Реализация функций:** Практическая реализация основных механизмов SPA (маршрутизация, управление состоянием) с использованием vanilla JS и паттернов проектирования без зависимостей от внешних фреймворков.
3.  **Инновационная админ-панель:** Интеграция клиентской системы управления контентом напрямую в библиотеку — функция, не встречающаяся в основных альтернативах.
4.  **Инструментарий для продакшена:** Настроенный пайплайн сборки и развертывания, обеспечивающий качество кода, совместимость и производительность.
5.  **Комплексная валидация:** Библиотека была обоснована через сравнительный анализ, UML-моделирование и многоаспектный тестовый режим.

Библиотека особенно подходит для **образовательных контекстов** (для понимания внутреннего устройства SPA), **быстрого прототипирования** и **легковесных проектов**, где сложность крупных фреймворков не оправдана. Она служит доказательством возможностей современного vanilla JavaScript и предоставляет основу, которая может быть расширена такими функциями, как Virtual DOM diffing или серверный рендеринг (SSR) в будущей работе.
