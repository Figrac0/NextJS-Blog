## 🚀 Обзор

**Your Places** — это full-stack MERN-приложение, спроектированное как платформа для открытия и сохранения мест, а не как простое CRUD-упражнение. Пользователь может создать аккаунт, загрузить фото профиля, сохранять интересные места с описаниями и адресами, просматривать коллекции других людей и задавать встроенному ассистенту вопросы на основе мест, которые уже хранятся в системе.

Проект объединяет несколько продуктовых слоёв в один цельный опыт:

- публичную главную страницу с открытием контента и избранными блоками
- каталог сообщества, который превращает пользовательские данные в исследование
- приватные и публичные коллекции мест
- карточки мест с изображениями и реальными адресами
- интерактивный просмотр на карте
- гибридного ассистента, который работает как с живой LLM, так и без неё

Это делает приложение сильным full-stack проектом для портфолио, потому что оно связывает UX, архитектуру бэкенда, облачное хранение медиа, карты, деплой и локальную AI-интеграцию в один продукт.

## 🏗️ MERN-архитектура

Приложение разделено на две независимо разворачиваемые части:

- `mernFront` - React-клиент
- `mernBack` - Express и MongoDB API

![MERN-архитектура и поток работы платформы](MERN.png)

На верхнем уровне система работает так:

```text
React Frontend -> Express API -> Mongoose -> MongoDB Atlas
                     |             |
                     |             +-> Коллекции пользователей и мест
                     |
                     +-> Cloudinary для фото профиля и изображений мест
                     +-> Nominatim для геокодирования адресов
                     +-> Ollama для локальных AI-ответов
```

Такое разделение важно, потому что оно делает ответственности прозрачными:

- фронтенд отвечает за навигацию, состояние UI, формы и рендеринг
- бэкенд отвечает за валидацию, аутентификацию, авторизацию, хранение и внешние интеграции
- слой хранения медиа отделён от самого веб-приложения
- live AI остаётся опциональной возможностью, а не жёсткой runtime-зависимостью

### Структурный обзор

```text
MERN/
├── mernFront/
│   ├── src/home
│   ├── src/user
│   ├── src/places
│   └── src/shared
└── mernBack/
    ├── controllers
    ├── routes
    ├── models
    ├── middleware
    ├── scripts
    └── util
```

## 🎨 Фронтенд-опыт

Фронтенд построен вокруг пользовательского продуктового сценария, а не вокруг набора разрозненных экранов.

### Маршрутизация и модель страниц

Клиент включает:

- публичную главную страницу
- каталог сообщества
- страницы пользовательских коллекций
- страницу создания места
- страницу редактирования места
- страницу аутентификации

Такая структура маршрутов превращает приложение в маленькую платформу, а не просто в демо с формами.

### Клиентское состояние

Фронтенд использует:

- React state для рендерингового потока
- Context для аутентификации
- `localStorage` для сохранения сессии
- custom form hooks для валидации
- отдельный HTTP hook для загрузки и обработки ошибок

Такой подход сохраняет кодовую базу лёгкой, но при этом даёт приложению предсказуемое поведение.

### Ответственность UI

Фронтенд отвечает за:

- защиту маршрутов на уровне интерфейса
- восстановление логина после обновления страницы
- превью изображений перед загрузкой
- фильтрацию и сортировку коллекций
- отображение действий только для владельца
- рендер модальных карт по сохранённым координатам
- переключение ассистента между live и fallback-режимом

## ⚙️ Реализация бэкенда

Бэкенд следует понятной Express-структуре с routes, controllers, models, middleware и utilities.

### Основные обязанности

Сервер отвечает за:

- валидацию запросов
- проверку JWT
- авторизацию на основе владельца
- сохранение в MongoDB
- геокодирование
- загрузку и удаление медиа
- проксирование ассистента к Ollama

### Модель данных

Проект опирается на две основные коллекции:

- `User`
- `Place`

Один пользователь владеет множеством мест, и каждое место хранит:

- title
- description
- image
- image public ID
- address
- coordinates
- creator reference

Это позволяет наполнять пользовательские коллекции, рендерить карточки с медиа и безопасно применять правила владения.

### API-слой

Бэкенд открывает маршруты для:

- пользователей
- мест
- статуса ассистента и чата с ассистентом

API также спроектировано так, чтобы хорошо работать на Vercel, где бэкенд разворачивается как отдельный проект и подключается к MongoDB Atlas и Cloudinary через переменные окружения.

## 🔐 Аутентификация и авторизация

Аутентификация использует классический поток на основе JWT.

### Поток регистрации

1. Клиент отправляет `FormData` с именем, email, паролем и фото профиля
2. Бэкенд валидирует входные данные
3. Пароль хешируется через `bcryptjs`
4. Изображение загружается и сохраняется
5. Пользователь записывается в MongoDB
6. На фронтенд возвращается JWT-токен

### Поток входа

1. Клиент отправляет email и пароль в формате JSON
2. Бэкенд загружает подходящего пользователя
3. Пароль сравнивается с хешем
4. Генерируется новый JWT
5. Фронтенд сохраняет токен, user ID, время жизни и изображение профиля

### Правила авторизации

Защищённые маршруты используют Bearer tokens, а бэкенд проверяет, что:

- пользователь может создавать место только для себя
- пользователь может редактировать только своё место
- пользователь может удалять только своё место

Это один из самых важных моментов проекта, потому что именно он превращает приложение из UI-демо в полноценную многопользовательскую систему.

## 🗺️ Места, карты и геокодирование

Места являются центром продукта, поэтому приложение работает с ними как с более богатыми сущностями, чем просто текстовые записи.

### Пайплайн создания места

Когда пользователь создаёт место:

1. Фронтенд собирает текстовые поля и изображение
2. Запрос отправляется как `multipart/form-data`
3. Бэкенд валидирует payload
4. Адрес геокодируется через Nominatim
5. Координаты сохраняются вместе с остальными данными места
6. Изображение сохраняется и связывается с документом
7. Место становится частью коллекции владельца

### Интеграция карт

Каждое место можно открыть в модальном окне с картой. Фронтенд использует Leaflet и тайлы OpenStreetMap, чтобы отобразить локацию по сохранённым значениям широты и долготы.

### Интеллект на уровне коллекций

Фронтенд также строит дополнительную пользовательскую ценность из данных о местах:

- извлечение города из адресов
- лёгкая категоризация мест
- ранжирование лучших мест
- подсказки о том, какое место стоит добавить следующим

Это придаёт приложению более редакторский характер, вместо того чтобы оставлять данные полностью сырыми.

## 🤖 Архитектура AI-ассистента

Одна из самых сильных частей проекта — стратегия ассистента.

### Live-режим

В локальной разработке ассистент может использовать настоящую LLM через Ollama. Фронтенд проверяет доступность ассистента и отправляет:

- вопрос пользователя
- компактный список пользователей
- компактный список сохранённых мест

После этого бэкенд собирает чистый prompt и запрашивает ответ у локальной модели.

### Fallback-режим

Когда Ollama не запущен или проект развёрнут на Vercel, ассистент не ломается. Вместо этого фронтенд переключается на встроенный рекомендательный слой, который всё равно может отвечать на практические вопросы, например:

- какие места выглядят самыми сильными
- какие адреса уже сохранены
- в каком городе покрытие самое широкое
- какое место стоит добавить следующим

Такой гибридный дизайн делает фичу реалистичной для локальных экспериментов и одновременно надёжной в production.

## 🖼️ Хранение медиа и деплой

Медиа-слой спроектирован и для локальной работы, и для облачного развёртывания.

### Хранение изображений

Бэкенд поддерживает два режима хранения:

- **Режим Cloudinary** для production-ready постоянного хранения
- **Локальный fallback-режим** для более простых сценариев локальной разработки

В режиме Cloudinary:

- загрузки используют memory storage через `multer`
- бэкенд сам подписывает Cloudinary-запросы
- база данных хранит URL изображения и `public_id`

В локальном fallback-режиме:

- файлы по-прежнему могут храниться в директории uploads на бэкенде
- проект остаётся простым для запуска в локальной разработке

### Модель деплоя

Рекомендуемая production-конфигурация такая:

- `mernBack` как один проект на Vercel
- `mernFront` как второй проект на Vercel
- MongoDB Atlas как база данных
- Cloudinary как провайдер хранения изображений

Такая схема позволяет приложению работать почти так же, как и локальная версия, с одним намеренным исключением:

- Ollama остаётся локальным
- ассистент в production переключается на встроенный режим, основанный на данных о местах

### Путь миграции

Проект также включает скрипт миграции для переноса старых локально сохранённых изображений в Cloudinary, что особенно важно при подготовке приложения к реальному деплою.
