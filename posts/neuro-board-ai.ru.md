## 🚀 Обзор

**NeuroBoard AI** — это рабочее пространство продавца для управления объявлениями со встроенным AI-ассистентом. Приложение построено вокруг практического сценария улучшения контента: открыть список объявлений, изучить карточку товара, доработать публикацию, попросить AI улучшить текст или подсказать цену и сохранить результат обратно в систему.

Вместо того чтобы показывать AI как декоративную функцию, проект встраивает его прямо в повседневный процесс редактирования продавца. В результате получается продукт, который объединяет управление каталогом, UX редактирования, контекстные рекомендации и реалистичную локальную AI-интеграцию.

Платформа объединяет несколько продуктовых идей в одном интерфейсе:

- дашборд объявлений с поиском, фильтрами, сортировкой и пагинацией
- сфокусированную страницу просмотра товара
- сценарий редактирования с автосохранением черновиков
- AI-инструменты для генерации и улучшения описаний
- AI-оценку цены с устойчивым парсингом ответа
- контекстный чат-ассистент для конкретной карточки товара
- demo-friendly режим фронтенда, который остаётся рабочим даже без backend

Это делает NeuroBoard AI не просто админ-макетом. Это полноценный продуктовый прототип, который показывает, как инструменты для продавца, хорошая архитектура фронтенда и практичная LLM-интеграция могут работать вместе.

## 🧠 AI-возможности

Самая сильная сторона проекта — способ, которым AI встроен в конкретные действия продавца.

### Генерация описания

Если у объявления мало текста или его нет вовсе, ассистент может создать более ясное описание на основе уже заполненных структурированных полей карточки.

### Улучшение описания

Если текст уже есть, ассистент может переписать его в более аккуратную, читаемую и убедительную версию, сохранив реальные факты о товаре.

### Подсказка по цене

AI может предложить рыночно ориентированный диапазон цен и вернуть:

- рекомендованную цену
- минимальную и максимальную границу диапазона
- уровень уверенности
- короткое объяснение

Здесь используется устойчивый парсинг, потому что локальные модели не всегда возвращают идеально валидный JSON.

### Контекстный чат

Продавец может задавать уточняющие вопросы в контексте конкретного объявления. Это значит, что ассистент отвечает не абстрактно, а опирается на активную карточку товара и её недавнюю историю сообщений.

### Почему AI-слой действительно важен

Такой дизайн делает ассистента практичным, потому что он помогает решать реальные проблемы продавца:

- слабые или пустые описания
- неуверенность в цене
- отсутствующие поля в карточке
- непонимание того, как улучшить объявление перед публикацией

## 🏗️ Архитектура

Проект разделён на два понятных слоя:

- `frontend` - SPA на React + TypeScript
- `server` - лёгкий Node.js backend, повторяющий ожидаемый API-контракт

На верхнем уровне поток выглядит так:

```text
React SPA -> Query/Data Services -> Mock Node.js API -> JSON storage
     |
     +-> Локальное хранение черновиков в localStorage
     +-> Интеграция с Ollama для AI-функций
     +-> Demo fallback mode для статического деплоя
```

### Ответственность фронтенда

Фронтенд отвечает за:

- маршрутизацию
- рендер списка объявлений и карточек
- логику редактирования формы
- локальное сохранение черновиков
- переключение темы и языка
- управление состояниями запросов
- вызовы AI из контекста конкретного товара

### Ответственность бэкенда

Бэкенд отвечает за:

- `GET /items`
- `GET /items/:id`
- `PUT /items/:id`
- раздачу локальных изображений
- хранение seed-данных в JSON-файле

Это даёт проекту практичную модель работы: он может полноценно запускаться локально, но при этом фронтенд остаётся готовым и к отдельному демонстрационному размещению.

## 🎨 Фронтенд-опыт

Фронтенд построен как рабочий сценарий продавца, а не как набор разрозненных страниц.

### Модель страниц

Приложение включает три ключевых маршрута:

- `/ads` - дашборд продавца с поиском и фильтрацией
- `/ads/:id` - подробный просмотр товара
- `/ads/:id/edit` - пространство редактирования с AI-инструментами

### Стратегия состояния и форм

Клиент использует современный и при этом лёгкий стек:

- `Zustand` для состояния приложения
- `TanStack Query` для работы с HTTP-данными
- `React Hook Form` для управления формой
- `Zod` для схем валидации

Это делает архитектуру предсказуемой без лишнего усложнения проекта.

### UX-решения

Несколько решений делают приложение более продуктовым:

- восстановление черновиков защищает от потери работы
- незавершённые объявления визуально помечаются
- действия продавца остаются сфокусированы вокруг одной карточки товара
- кастомные поля дают точнее контролировать интерфейс
- страница редактирования становится естественным домом для AI-помощника

## ⚙️ Бэкенд и слой данных

Бэкенд здесь намеренно компактный, но при этом он не декоративный.

### API-контракт

Проект реализует ровно те маршруты, которые нужны для рабочего сценария продавца:

- получить список объявлений
- получить одно объявление
- обновить объявление

Этого достаточно, чтобы фронтенд опирался на реалистичную request-response модель, а не жил только на локальном фейковом состоянии.

### Модель хранения

Для этого проекта используется хранение в JSON. Такое решение выбрано ради воспроизводимости и простоты. Оно делает проект удобным для локального запуска и прозрачным для просмотра во время разработки.

### Зачем нужен локальный backend

Наличие backend даёт проекту два важных качества:

- фронтенд можно разрабатывать и проверять против настоящего API-контракта
- всё приложение остаётся полностью запускаемым локально без внешней инфраструктуры

Для портфолио-проекта это особенно ценно, потому что рабочий сценарий легко воспроизвести и легко проверить.

## 🔄 Demo mode и стратегия деплоя

Одна из сильных деталей проекта — разделение между полноценным локальным режимом и публичным demo-режимом.

### Полный локальный режим

При локальном запуске приложение рассчитано на работу вместе с:

- фронтендом
- mock backend
- Ollama для live AI-функций

Именно так раскрывается полная интерактивная версия продукта.

### Hosted demo mode

Для Vercel и других сценариев статического размещения проект может переключаться в frontend demo mode. В таком режиме:

- интерфейс по-прежнему открывается корректно
- sample-объявления остаются доступными для просмотра
- страницы деталей и редактирования продолжают работать как UX-витрина
- локальное хранилище может имитировать изменения через browser storage
- продукт остаётся пригодным для показа даже без live backend

Это сильное продуктовое решение, потому что оно разделяет потребности презентации и локальной разработки, не ломая интерфейс.

### Docker и воспроизводимость

Проект также включает `docker compose`-сценарий для одновременного запуска клиента и сервера, что повышает воспроизводимость окружения и упрощает передачу проекта другим людям.
